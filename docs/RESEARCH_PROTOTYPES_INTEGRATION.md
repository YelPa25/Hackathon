# ASTRA 2.0 research prototype integration plan

Status: Architecture approved in principle. Updated after source review. Scope is handoff preparation.

## Verified starting point

- The last local Core checkpoint inspected was `5e61fb3`, which includes Stage 03 replay at `f348eaa` and the verified runtime dataset. GitHub `main` is `03d3be4`, and its one additional commit changes `README.md`.
- The application has four routes in [screens.ts](../frontend/src/pages/screens.ts): Mission Overview, Crew Health, Mission Replay, and Data & Science. Crew Health shows measurements, data quality, charts, and detailed records. Mission Overview reads a core snapshot with crew and cabin observations. The current `insights` list is empty, and the crew analysis endpoint, core personal baselines, trends, and statuses described in [the contracts](CONTRACTS.md) are planned. Guided Assessment, case management, and Earth Reporting are outside scope.
- [Database reads](../backend/src/astra/db.py) use a read-only SQLite connection and transaction. [The API](../backend/src/astra/routes.py) reads the replay state and rows in that transaction. [Observation queries](../backend/src/astra/reads.py) enforce the dataset and inclusive UTC cutoff, exclude private health rows from broad reads, and order by timestamp and observation ID. The pagination revision guards against mixing snapshots. The [replay writer](../backend/src/astra/replay.py) advances or resets the cursor and publishes rows atomically. The frontend follows the backend cursor through [ReplayProvider](../frontend/src/app/ReplayProvider.tsx).
- The existing backend uses Python 3.12, FastAPI, Pydantic, Uvicorn, and SQLite. The UI uses React, TypeScript, Vite, Tailwind CSS, and Recharts. The tracked bundle covers a fictional crew and 90 days of synthetic data. Replay starts at UTC close on Day 45 with 6,252 observations. The later 6,239 observations are private replay inputs. Vite serves from the frontend directory and excludes source CSV requests. Core's local HTTP routes do not currently enforce per-worker authorization. The development CORS settings are for browser access.
- The two teammate branches each add a standalone directory from `5e61fb3`. Neither prototype is part of GitHub `main`. This is a source review. Windows runtime and model output validation are pending.

**Physiology coverage.** The ASTRA metric dictionary has no respiration-rate or prior-day radiation-dose metric. The supplied scorer rejects an incomplete snapshot and expects a finite value for every field. Heart rate context, blood pressure pairing, and the timing of intermittent observations also need a defined mapping. The bundled heads are `person_1` through `person_3` and `global`. ASTRA's four crew IDs have no verified mapping, and the scorer silently uses the global head for unknown IDs. Keep live scoring unavailable until the teammate provides a supported feature contract, missing-data policy, time alignment and calibration for the ASTRA profiles. The supplied training code generates synthetic labels from three source profiles and adjusts the model using grouped folds. The README describes no independent test set. Obtain the dataset lineage and held-out evaluation before describing this as prospective performance.

**Explanation and sensitivity.** The cabin comparison varies three inputs toward a nominal vector and checks for a threshold crossing. Describe the change as a model response to hypothetical inputs. On flagged results the scorer calls local Ollama at port 11434 for `qwen3:4b`, with a 60-second timeout and template fallback. Start with a deterministic explanation. Verify that an explicit offline mode skips the Ollama call, that the UI can distinguish a template from generated text, and that generated output is checked for meaning as well as supported numbers before enabling it.

**Behavior runtime and time alignment.** The face and speech handoff has documented macOS CPU runs. It pins Torch 2.0.1, MediaPipe 0.10.5 and LibreFace 0.2.0. Review the supported Windows interpreter and wheel combination separately from Core's Python 3.12. Start with CPU and verify the RTX 5090 Laptop setup separately. The speech extractor can resolve Silero VAD through Torch Hub and XLS-R through Hugging Face, so require reviewed pinned local artifacts before enabling offline extraction. Request license and permission evidence for the committed weights and recorded media. Use source recording timestamps and distinct fixture subjects. ASTRA has no facial or voice capture timeline mapped to its 2040 replay, so keep these findings on the research screen until a verified mapping exists.

## Proposed boundary and layout

Keep ASTRA Core as the authority for profiles, observations, the replay clock, and any future Core health analysis. Start with the existing CLIs and a small adapter for each. Run each in its own environment and directory, on demand. For the fixture phase, explicit input/output files and the existing command exit status are sufficient. Add a small launcher or local bridge only when the UI needs it. Reuse the native interfaces and model implementations. Keep approved experimental outputs in a dedicated directory outside Git and Core storage.

| Proposed location | Responsibility |
| --- | --- |
| `research/adapters/{physiology,behavior}/` | Translate the verified JSON or JSONL boundary into a small, versioned result envelope. |
| Separate reviewed teammate checkouts or pinned source directories | Preserve each CLI, model files and dependency manifest. |
| User-local research directory outside the repository | One input/output folder per run. Keep sample media, per-subject detector state, caches and weights here. |
| Optional Core snapshot helper and UI bridge | Add a narrow read-only snapshot export and result reader only when a module qualifies for ASTRA data and the UI needs the bridge. |

Launch workers apart from the Core process. Give each worker its materialized inputs, pinned weights and working directory. Enforce read restrictions through a separate local account or an equivalent Windows process boundary before granting access to live inputs. Restrict direct Core HTTP and external network access for those workers. SQLite's read-only connection and loopback are insufficient on their own because the existing Core API can mutate replay. Keep a timeout, per-run output limit, cancellation and plain status. Core startup, replay and charts remain independent of workers. Retain the native face dashboard for separate review instead of embedding its capture behavior in ASTRA.

## Two explicit input modes

**Mission Replay Mode.** The trusted launcher asks the Core snapshot exporter for a bounded list of allowed metrics and contexts for a selected subject, optionally including aligned cabin readings. Core validates the module, subject and allowed fields, takes its own cursor from `read_snapshot`, and exports rows from `visible_observations` in that same transaction. Materialize a small, immutable bundle, then close the transaction before starting model work. The requester cannot set a later cursor. The exporter gives a worker the bundle by file or stdin, never DB credentials, a source path, or the existing general-purpose API. Allow only necessary observations. Prefer `include_private=False`. Any private self-report needs a reviewed purpose, explicit subject scope and authorization. Cabin sharing metadata does not permit displaying raw private scores on Mission Overview. Use existing subject identifiers and preserve observation IDs, UTC timestamps, context, quality, nulls, units, and synthetic provenance. Reject unknown metrics, wrong subjects, oversized windows, and future references.

A proposed version 1 snapshot records `snapshot_id`, `mode`, `dataset_id`, `dataset_fingerprint`, `subject_id`, `captured_at_utc`, `replay_revision`, `mission_day`, `cutoff_utc`, `window_start_utc`, `window_end_utc`, feature scope, and authorized observation rows or a referenced immutable local bundle. The host records input row IDs and hashes. Use the backend cutoff or a smaller approved bound for all feature windows. Any averaging, rolling feature, gap policy, training, imputation, normalization, calibration, threshold selection, and explanation context must use eligible inputs for that evaluation time. Freeze the calibration boundary before scoring and require training manifests with window bounds and subject/session split. A checkpoint trained or tuned on future mission data, or with unresolved lineage, can only be presented as retrospective. Rerunning it on a visible prefix cannot establish prospective validity.

**Full Dataset Research Mode.** Require explicit selection on the research page. Use a different API namespace, job type, permissions, run directory, and result partition. A trusted research exporter can verify the two prerecorded partitions and provide a bounded, read-only research snapshot through Day 90 with a dataset fingerprint and explicit UTC window. Keep this separate from the Core observation API and replay state transaction path. A worker need not open the real source directory. Leave archives, generator outputs, and evaluation truth out of both inference bundles. A future separately reviewed offline evaluation could compare predictions with labels in another step. Use entirely separate model cache namespaces for mode-dependent training, normalization or calibration artifacts. An approved immutable weight file can be reused across modes only if its attested lineage qualifies for the mode.

Suggested API surface, with exact names subject to review:

| Interface | Access and purpose |
| --- | --- |
| `POST /internal/research/v1/replay-snapshots` | Trusted launcher only. A narrowly authorized snapshot request. Reject unknown fields and a client-supplied cutoff. It has no Core write side effects. Keep internal transport out of Vite. |
| `POST /api/research/replay/runs` and `GET /api/research/replay/results` | Optional UI boundary for eligible replay runs and visible results. The server binds results to the authorized snapshot. |
| `POST /api/research/retrospective/runs` and `GET /api/research/retrospective/results` | Explicit research-only controls and result space. Use separate authorization and server-side mode enforcement. |
| `GET /api/research/modules` and cancel a run in its owning namespace | Availability, supported modes and compute states. Cancel can affect only the identified research job. |

## Version 1 result envelope

The adapter host assigns or validates host-owned fields at the adapter boundary. Accept versioned, typed, bounded JSON and use finite numeric values. Store native artifacts separately behind a reviewed detail view.

| Field | Meaning and validation |
| --- | --- |
| `schema_version`, `result_id`, `run_id` | Contract version and unique run/result identifiers. Retries for the same model, input bundle, configuration and finding can deduplicate. |
| `module_id`, `module_version`, `model_version`, `artifact_digest`, `config_version` | Pinned worker, weight, configuration and calibration identity. Record Qwen and prompt-template versions separately when used. |
| `subject_id`, `mode`, `snapshot_id`, `dataset_fingerprint`, `input_origin` | Host validates the authorized subject and snapshot. Input origin distinguishes synthetic mission records, research fixtures, and opt-in live media. |
| `created_at_utc`, `analysis_window_start_utc`, `analysis_window_end_utc` | UTC compute time and input times. Record `mission_day`, `cutoff_utc`, and `replay_revision` for replay. Use null for replay-only fields in retrospective results. Capture timestamps use their own clock. |
| `status`, `error` | Status is `AVAILABLE`, `LOADING`, `RUNNING`, `SUCCEEDED`, `UNAVAILABLE`, `ERROR`, `INSUFFICIENT_DATA`, or `CANCELED`. Errors carry a stable code and a display-safe message. An unsuccessful result has nullable score and finding. |
| `input_refs`, `quality`, `limitations`, `lineage` | Host validates evidence against the assigned bundle and permissions. Quality may carry sample counts, missing inputs, coverage, synchronization quality, or signal quality. Lineage carries training, normalization, and calibration bounds or an explicit unknown. |
| `score`, `finding`, `numeric_evidence`, `explanation` | A score has name, finite value, scale or unit, interpretation, threshold version and calibration version where applicable. Findings use module-specific terms such as experimental deviation. Numeric evidence includes units and allowed provenance. Explanation is optional plain text and records its generation state. |
| `module_details` | Validated module-specific details, versioned separately. Examples include calibrated score, hypothetical substitutions and output deltas, or CUSUM, embedding drift and hysteresis. Keep raw recordings, private features and diagnostics behind the appropriate research policy. |

The physiology adapter should wrap the reported shared XGBoost model and per-astronaut calibration. Verify the actual feature order, time alignment, preprocessing, missing-data treatment and score semantics against the handoff. Habitat sensitivity uses reviewed substitution values in a copy of the feature vector. Show original and hypothetical inputs, units, the score change, and the label **Model sensitivity under hypothetical cabin inputs**. The result describes the model response to the substitution. Any Qwen step receives a limited validated evidence payload and output template. Preserve numerical evidence independently, reject unsupported numeric claims or health directives, and show an unavailable explanation when validation or inference fails. The LLM has no tool access or authority to execute actions.

The behavior adapter should translate the documented JSONL records into the envelope and confirm the mapping against a fixture. Preserve enough identifiers to track input windows and individual calibration, and retain module-specific field names in the research detail payload. Validate JSONL line length, schema, order, timestamp clock, subject mapping, nulls, invalid numerics, duplicates and partial jobs. Test whether worker state such as CUSUM, Mahalanobis drift and hysteresis can be checkpointed or replayed without cross-subject, cross-mode, or post-reset contamination. Facial action units and speech features are experimental signal changes. They cannot support clinical mental-health or illness claims.

## Dashboard and research UI

Add **Research Prototypes** to the existing dark navy/cyan sidebar after approval. Use five panels with independent readiness and output states. Personalized ML Alerts runs on an explicitly selected astronaut and input mode. Habitat Sensitivity reruns only experimental inference with approved substitutions. Local AI Explanations can be run or skipped independently. Facial Feature Monitoring and Voice Feature Monitoring start with approved fixture playback. If approved later, each hardware panel gets separate Start and Stop, an active capture indicator, and a session-specific notice covering source and retention. Default to permission off, memory-only capture where feasible, and automatic cleanup of any approved temporary raw files on stop, cancellation, and expiry. Keep stored recordings, credentials, and model caches out of Git. Live capture uses wall-clock session metadata and stays out of historical replay comparisons. External media transfer requires explicit approval.

Show compact cards labeled **Experimental** in Mission Overview and Crew Health with a recent eligible Replay Mode result, its model and mission day, and a link to research details. Mission Overview uses a shareable summary only. Crew Health applies subject scope and privacy checks. Retrospective results appear only inside Research Prototypes. The UI clearly separates research status from current health observations and any later Core findings. If there is an appropriate Core finding and experimental result for the same published inputs, show both with their evidence windows and disclose disagreement. The present application has no authoritative health status to compare. Use a short state message or suppress an unavailable optional card. Avoid placeholder scores, automatic health actions, and a blended health score.

The host validates eligibility on every result read: dataset fingerprint, mode, subject, privacy, input authorization, and snapshot cutoff at or before the current Core cursor. Track a replay generation that changes on reset, or revalidate the complete input manifest and invalidate earlier runs when the cursor rewinds. Stage 03 increments a revision on commands as well as time changes, so revision alone is too strict for showing a result from an earlier visible day and too weak to describe run continuity. Label earlier visible results with their input day and age. Discard or quarantine a completion from an invalidated generation, including a result that lands just after reset. Recheck on the UI's published cursor update. Never change `/api/mission` Core fields or the existing charts to contain experimental scores.

Keep one virtual environment and lockfile per worker. Record model IDs, revision, hashes, licenses, sizes and retrieval commands before any download. Benchmark CPU fallback, VRAM, cold-start time, inference latency and simultaneous use with replay. Start with fixed limits and one GPU-heavy job at a time until measurements justify concurrency. Keep the Core install and startup sequence independent.
