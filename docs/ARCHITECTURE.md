# ASTRA 2.0 architecture

ASTRA is an offline, non-clinical prototype for a fictional four-person transit. It opens at the close of Day 45 with 45 days of recorded history. Crew can replay Days 46–90 and inspect how personal measurements and cabin conditions change. All mission readings and crew profiles in this release are research-informed synthetic data. The dataset's NASA and CDC references explain measurement choices and published context. They do not validate the synthetic individuals, a clinical decision process, or correlations as causal effects.

## Boundaries

- React, TypeScript, Vite, Tailwind CSS and Recharts render the four screens. Their API client reads backend DTOs. Browser state holds presentation preferences and requested filters.
- Python 3.12, FastAPI and Pydantic validate requests and ingest source data. Use Python's SQLite driver and SQL migrations. A single local backend owns the mission clock, measurements and analysis. The normal demo listens on loopback and uses the built frontend with same-origin API requests. During development Vite proxies the API locally.
- The dataset directory is immutable runtime input, outside the frontend's public assets and static mount. Configure its path for the checked-out layout. Stage 02 startup reads the crew profiles, metric dictionary, manifest, scientific source catalog and historical partition. It verifies these five files against the supplied checksum list before publication. SQLite stores source decimals as text and observation responses expose them as JSON numbers. Only the replay service can read the future partition and select the next scheduled batch. Observation, baseline, trend and UI services have no source-file fallback. Distribute no runtime support for the evaluation CSV, full archive, generator, workbook or review summaries. Use selected validation metadata only for static provenance documentation, without future aggregates or event labels in live screens.
- SQLite holds dataset metadata, crew, dictionary, a singleton replay state and revealed observations. Add a stable source ID key and indexes for timestamp and per-subject metric queries. A lightweight source adapter validates the CSV and maps it to internal DTOs. Keep future rows in the source partition until the replay writer is about to publish a batch. A read-time cutoff independently protects every query.
- Deploy no cloud service. Use installed Windows Python 3.12 with a venv. If using uv, select the installed interpreter with `--no-managed-python`. Network access is for initial setup and optional official source links. Core startup and mission operations require no LLM. ASTRA Companion can use an optional local model for recreation.

## Data flow

1. Atomically install verified metadata and historical rows, initialize the cursor to Day 45 UTC close, and start paused. Persist checksums for runtime inputs. On restart recheck source hashes and reuse the committed import. Stage 03 restores prior playback in PAUSED state. Failing validation leaves the last committed state available and reports a dataset error. A bootstrap failure blocks mission reads. SQLite schema version 2 adds playback speed, a pinned future checksum, and a replay ownership table in place.
2. The single long-lived FastAPI process owns a monotonic timer. The replay service lazily verifies and privately indexes the prerecorded partition, validates each publication batch with the historical source adapter, then inserts exact rows, records ownership, and advances the cursor in one transaction. The first verified future checksum is pinned in SQLite. Reset removes only owned rows and restores the historical cursor. A failed write leaves the prior cursor and observations intact. Repeating an operation with a stale revision fails before writing. Group simultaneous rows in one batch and use source IDs for ties.
3. Read the replay cursor and observations in one database snapshot. The common read service adds `timestamp_utc <= cursor` even though only published rows belong in SQLite. Mission cards, cabin summaries, crew charts, insights and any later export or AI context use that service. Paginated reads guard against revision changes. The browser polls replay state and refreshes snapshot-backed panels when the published cursor changes.
4. The [native Stage 04 engine](HEALTH_INTELLIGENCE_METHODOLOGY.md) computes robust fixed Day 1–45 references by crew, metric and context. It reads only published records in the current SQLite read transaction, calculates trends, contextual findings and distinct cabin evidence on demand, and never writes records or changes the cursor. Mission summaries use shareable rows; selected-crew analysis is separate. Versioned policy lives in the backend. If analysis fails, Mission Overview still returns crew/cabin observations, and Crew Health can still load its raw measurements and charts. No schema change, cache, model, external service or extra worker is needed.

## Screen specification

Use one shell with four Core navigation entries. Research Prototypes is a separate optional experimental section. ASTRA Companion adds a recreational chat destination to the same sidebar. Use premium dark navy surfaces, restrained cyan accents, high-contrast text and amber for follow-up or measurement quality. Every chart names the metric, unit and UTC range, marks gaps and uses accessible labels. Keep the current mission day and synthetic status visible. Support keyboard navigation and a readable single-column layout on narrow screens.

| Screen | Information and actions |
| --- | --- |
| Mission Overview | Show the simulated clock, playback state, four crew summaries, latest available cabin metrics and concise findings. Distinguish missing and stale data from valid readings. Link directly to a selected astronaut in Crew Health. |
| Crew Health | Select an astronaut and metric or activity context. Show the latest reading with time, source and quality, visible history, the personal reference and a short explanation of any change or coverage gap. Keep private self-reports in the selected profile's view. |
| Mission Replay | Start at Day 45 and show play, pause, next timestamp, next day and reset. List revealed events in chronological order. Show that future records are locked without exposing their contents, timestamps or scenario labels. Speed selection can follow core verification. |
| Data & Science | Distinguish the published bundle inventory from the live replay cutoff. Show synthetic provenance, NASA’s five hazards, native methods and limitations, a read-only hypothetical comparison, the metric dictionary, checkpointed validation, reviewed references, and AI-assisted development attribution. The page uses local assets and APIs. Source links are optional outbound navigation. |

Scope ends at measurements, trends and explainable findings. Guided medical assessment, medical cases and checklists, Earth reporting and communications, biometric emotion recognition, mandatory LLMs and unvalidated disease prediction are excluded.
## Science comparison

The Data & Science comparison reads the replay-gated, shareable Days 1–45 resting-heart-rate history in a single SQLite snapshot and calls the same baseline and deviation functions used by native analysis. The hypothetical reading is passed directly to the calculation. It is neither stored nor used by production monitoring. The endpoint returns reference summaries; it exposes no raw observations, private reports, or future records.

## ASTRA Companion

Companion is the only browser route that calls `/api/companion`. The browser keeps the draft, transcript and pending request in application memory across page navigation. It sends the current message and bounded complete user/assistant pairs. Closing or reloading the app or choosing New Conversation clears the transcript.

FastAPI uses a separate router and a direct HTTP connection to `127.0.0.1:11434`. Status queries list installed models without loading one. Inference uses only the exact local Qwen tag described in the contracts. Each request receives a fixed recreational system prompt and the supplied transcript. The service has no mission dependencies or tools. It has no storage or credentials for chat. Runtime egress is limited to its fixed loopback destination. The frontend renders reply text through React and has no external chat assets.

One generation can run per ASTRA backend process. FastAPI runs the blocking Ollama request in a worker thread so replay, dashboard queries and health analysis can proceed. Failure responses stay in the Companion panel for retry. Ollama can start on demand and briefly retains the loaded model after replies.
